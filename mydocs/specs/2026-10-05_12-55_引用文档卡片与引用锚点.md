## 2. Research Findings（均已核实，附 file:line）

### 2.1 链路选择：只能改 TS 侧

`README.md`（`2019d78` 刷新）明确：三个前端 Vite 代理均指向 `:8000` 即 TS 后端；**Python 端（`:8004`）没有前端接入**。故链路定在 `apps/server`。

副证：Python 侧无 `content_block` 卡片协议、`hybrid_search` 仅委托纯向量检索（`server-py/src/rag/pgvector.py:97-109`）、`search_knowledge` 工具把 `doc_id/chunk_index` 全部丢弃（`server-py/src/agent/tools/builtins/search_knowledge.py:95-107`）。

### 2.2 引用卡片：数据在**工具层**就已丢失（v1 此处判断有误，已修正）

**字段来源本来齐全**：`KnowledgeSearchResult` 含 `chunkId / docId / kbId / content / score / chunkIndex / docTitle`（`services/knowledge.ts:27-35`）。`recallSources` / `parentChunk` 属 `HybridSearchResult`（`knowledge.ts:38-54`），不在本链路。

**真实的丢失点（三处，按数据流顺序）**：

1. **工具层（根因）**：`tools/builtin/search-knowledge-base.ts:44` 拿到完整 `rawResults`，但在 `:60-64` 组装 `deduped` 时**只保留 `{content, score, source: r.docTitle}`**，`:86-90` 序列化输出同样只有三个字段。**`docId` / `chunkIndex` 在此永久丢失**，下游不可能恢复。这是必须改的第一处。
2. **上下文构建层**：`knowledge-context.ts:18-22` 的 `RawKBResult` 只有 `content/score/source`；`build()` 在 `:70-76` 合成 `docId: 'kb-{i}'`、`chunkIndex: i`。即使上游修好，这里也要同步扩展类型与解析。
3. **`simple_qa` 路径**：`agent-executor.ts:611` 的 `searchResults.map((r) => r.content)` 只取正文，丢掉 `docTitle/score/docId`。**这是最简单的一处，也是让卡片最快能跑起来的一处。**

**关于前端"参考来源"面板为何永不显示（v1 表述有误，已修正）**：
`AgentChatPage.tsx:239-282` 的面板依赖 `msg.knowledge`，而 `meta.knowledge` 在 **TASK 路径下架构上装不下结果**——`RouteContext` 在 agent 执行**之前**构建（`agent-runtime.ts:450-465`），检索发生在 agent **内部**（`agent-executor.ts:609` / 工具调用）。`context.knowledgeResults` 的唯一读取方是 `diagnosis-agent.ts:200`（DIAGNOSIS 路由，已 grep 确认全仓仅此一处业务读取，其余均为测试里的 `[]`）。
→ **结论：TASK 路径不应去"透传 knowledgeResults"（v1 的错误改动项，已删除）。TASK 的唯一正确数据源是新增的 `citations` 事件。**

### 2.3 引用锚点：指令侧已就绪，解析与渲染侧缺失

- **已有**：`handleSimpleQA` 的 prompt 已要求标注编号 —— `agent-executor.ts:634`「如果知识库有相关信息，引用编号（如 [1]）」
- **缺失**：回答侧的 `[n]` 抽取（`citation-verifier.ts` 只把聚合统计写进 `done.citation`，不产出条目）；前端无 `[n]` → 可点击按钮的转换
- **可移植思路**：`knowledgeHub/.../SourceCiteList.tsx:150-202` —— 在 react-markdown 的**元素渲染器**层递归注入（`injectCites` 对 `children` 做 `Children.map`，对字符串子节点切分），而非对 markdown 字符串做 split

### 2.4 思考过程：可做，但**不是**模型思维链

- 原型展示的是**模型思维链**：`ai-stream.service.ts:96` 给 qwen 挂 `enable_thinking: true`，`:296 mapReasoningStream` 把 `reasoning_content` 改写为前端 reasoning 部件 → `ThinkBlock`。
- AgentForge **完全没有这条链**：两侧 provider 只读 `delta.content` / `delta.tool_calls`（`providers/deepseek.ts:147`、`providers/openai.ts:166`、`server-py/src/providers/openai_provider.py:134`），全仓 `reasoning_content` 零命中。
- **`agent_think` 不可用**：虽由 `legacy-agent-runner.ts:680` 产出、被 `agent-executor.ts:501` 丢弃，但在原生 tool-calling 路径下其字段是模板文案（`legacy-agent-runner.ts:504-519`）：`observation: "调用了工具 X"` / `analysis: "工具 X 返回了数据"` / `plan: "查看工具返回的数据并生成用户回复"`。真实 LLM 撰写的推理只出现在旧式文本 ReAct 路径。
- **`simple_qa` 完全不产生过程事件**：`handleSimpleQA`（`agent-executor.ts:597-720`）是直线——KB 检索 → `clear_stream` → token 流。

**结论**：v1 的"思考过程"实现为**检索/工具过程时间轴**（查了什么词、命中几篇、调用了什么工具），与用户描述的"去查阅相关数据"一致，数据全部已在手。模型思维链列为 Out-of-Scope。

### 2.5 章节标题（方案 B 的已知套路，本期不做）

原型能显示章节，是因为分块器顺带做了标题继承：`knowledgeHub/.../chunking.service.ts:95-104` 维护 `currentHeading`，块内遇 `#` 更新，后续无标题块前缀补上当前标题。AgentForge 的 TS 侧 `heading` **零命中**，要做需改分块器 + ES mapping + 重跑索引。

### 2.6 原型项目的版本落差（避免误判可借鉴范围）

`knowledgeHub` 前端引用的 `data-intent` / `data-eval` / `data-graph` / `rewrite_query` / `retrieve_knowledge` / `retrieve_graph` **后端从未实现**：查遍全部 4 个分支与旧快照 `C:\workspaces\knowledge-hub-backend-main`，后端零命中，`git log --all -S` 证明历史上从未提交。故本期三件事之外无遗漏的可移植实现。

### 2.7 持久化与回放

- **但历史回放路径当前不读 metadata**：`routes/agent-runtime.ts:96-118` 的 `select` 只取 `id/role/content/createdAt`，响应只映射 `{id, role, content, timestamp}`。P0-1 已纳入 §4.1。

- `types.ts:29 Citation` —— `KnowledgeContext` 的内部结构（含 `chunkIndex`），**保持不动**；新增一个显式映射函数 `toCitationCards(citations: Citation[])` 供协议层使用

### 3.2 协议扩展

在 `RouteStreamEvent` 新增两个事件，均为**追加**，不改既有事件语义：

```ts
// packages/shared-types/src/citations.ts
/** 引用卡片条目：index 与正文 [n] 一一对应 */
export interface CitationCard {
  index: number;      // 从 1 开始，与正文 [n] 一致
  docId: string;      // 真实文档 ID
  docTitle: string;
  excerpt: string;    // 摘录，限长约 200 字符
  score: number;
}

/** 过程时间轴的一步 */
export interface TraceStep {
  seq: number;
  kind: "retrieval" | "tool";
  label: string;                        // 中文描述，如「检索知识库」
  status: "running" | "done" | "failed";
  detail?: string;                      // 查询词 / 工具名
  hitCount?: number;
}
```

```ts
| { type: "citations"; items: CitationCard[]; message_id: string }
| { type: "trace_step"; step: TraceStep; message_id: string }
```

**设计取舍（含 v1 理由修正）**：
- `citations` 一次性数组：检索完成时全集已可得，正确。
- `trace_step` 增量单步：需逐条流式出现。
- **命名用 `trace_step` 而非 `trace`**：单步语义显式，避免与未来聚合事件混淆。
- **范式说明修正**：`diagnosis_phase` 是**成对事件**（`_phase` 开始 + `_phase_done` 结束），`trace_step` 是**单事件带可变 `status`**（running→done），两者是不同模式。前端需按 `seq` **更新已存在步骤**，这是 diagnosis 未用过的新交互模式——需在实现时明确处理。
- **不复用 `content_block`**：`ContentBlock` 是 LLM 产出的正文内富媒体卡片，走正文流且不进 `Message.metadata`；citations/traces 是**消息级元数据**（要持久化、要回放），语义不同。复用会污染 `content_block` 的边界并把回放路径卷进围栏卡片解析。
- **命名区分**：新 `citations`（逐条卡片）vs 既有 `done.citation`（L4 引证校验聚合统计，`types.ts:105-110`），同词不同粒度，需在协议注释里写明。

### 3.5 交互规则

- **`[n]` 过滤归属（P1-4 修正）**：`citations` 在 LLM 回答**之前**发出，后端此刻不可能知道 LLM 会标哪些 `[n]`。故过滤**在前端、回答完成后**执行：解析最终 content 的 `/\[(\d+)\]/g`，据此过滤 `citations`；**无任何 `[n]` 时回退为展示全部召回条目**。此步骤需写进 §4.2 checklist。
- 正文 `[n]` 点击 → 滚动到**本条消息**的对应卡片并 flash 高亮（不跳转文档）
- 无命中时：不渲染卡片区，时间轴显示"未检索到相关资料"
- 历史会话回放：从 `Message.metadata` 还原（依赖 §3.4 的 history 改动）
- **"查看原文"**：待 §0 决策。若取方案 A（推荐），卡片为纯展示，**不写死链、不留 stub**
