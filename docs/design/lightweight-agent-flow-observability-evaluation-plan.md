# 轻量 Agent 流程可观测与评测方案

日期：2026-10-10。
状态：讨论稿，尚未批准业务代码实施。
前置方案：`lightweight-agent-flow-plan.md`。

## 1. 目标与方向

管理端试运行和客服端调用已由用户验证通过。下一阶段围绕两个问题建设最小闭环：

1. 一次多 Agent 执行中，各节点接收了什么、调用了什么、如何选择分支、在哪里失败？
2. 修改角色、提示词、工具或节点关系之后，流程效果是否改善？

推荐复用 Langfuse 承担执行链路展示与评测结果分析；AgentForge 继续负责流程配置、发布、执行和运行状态。

本阶段不以接入真实核身监控系统作为前置条件。核身业务日志用于判断业务故障，Agent 可观测用于判断推理与工具执行过程，评测用于比较结果质量。未来有真实业务数据时，仍可作为诊断工具的输入接入。

## 2. 当前基础与缺口

| 能力 | 已有基础 | 本阶段需要补齐 |
| --- | --- | --- |
| 流程配置 | 角色、提示词、任务、工具、输入输出、分支、草稿和发布 | 用实际案例调整配置，暂不新增节点类型 |
| 本地运行记录 | 流程状态、节点输入输出、错误和耗时；管理端可查看历史运行 | 关联 Langfuse trace，标记试运行、正式运行与评测 |
| Python 可观测 | 已有 Langfuse Provider；ReAct 模型调用与工具执行已有埋点 | 配置流程入口与节点层级、失败状态、版本元数据 |
| TS 可观测 | 已有独立 Provider | 首版通过运行 ID 关联；跨语言统一 trace 后续按需补充 |
| 评测资产 | 已有评测设计、诊断检索脚本、知识库回归能力和运行时测试 | 增加针对配置流程的小数据集和独立评测入口 |

配置执行通过 Python `/api/agent-flows` 入口进入，不能因普通 Python 聊天入口有根 trace，就假定这条入口已完整观测。

已有埋点代表可复用基础，不代表实际链路已经正确关联或数据已成功上报。实施前需验证当前安装 SDK、Langfuse 服务版本、观测上下文、异步任务传播及生命周期。

当前 `query_trace_log` 使用模拟数据，未知 traceId 会返回默认样例。本阶段必须明确标记模拟来源；未知样例不能被评为“找到了真实日志”。

## 3. 最小交付范围

| 范围 | 交付内容 |
| --- | --- |
| 流程级追踪 | 每次执行或续跑有独立 trace，携带运行、流程、版本和执行模式 |
| 节点级追踪 | Agent、条件、结束节点记录输入输出、状态和耗时；条件记录所选分支 |
| 模型和工具追踪 | 归属实际执行的节点，记录调用参数、结果、错误和可取得的 usage |
| 管理端关联 | 在现有运行面板增加“查看执行链路”，继续使用本地记录展示即时状态 |
| 小规模评测 | 固定一版流程快照，对一组带预期结果的案例运行并产出报告 |
| 版本比较 | 对同一数据集比较两份流程快照，查看逐案例结果、失败原因和耗时 |

暂不建设独立可观测看板、通用评测工作流、自动优化提示词、定时任务、发布审批或全平台质量门禁。

首版优先使用已有 Langfuse 实例或托管服务。若需要新增自托管实例，部署与运维是独立投入，不能计作零基础设施成本；部署方式确认后再实施连接配置。

## 4. 执行与观测关系

```text
AgentForge 管理端 / 客服端
  -> 现有 TS API -> Python 配置流程执行器
    -> 流程 trace
      -> 前端 Agent 节点
        -> 模型调用
        -> 工具调用
        -> 模型最终回答
      -> 条件节点：记录分支判定
      -> 后端 Agent 节点（按分支执行）
      -> 综合分析节点（按分支执行）
      -> 结束节点

本地数据库：保存权威运行状态、配置快照和节点记录
Langfuse：接收观测数据，展示链路、评分与实验比较
```

观测是执行器旁路能力，不增加一个需要管理员连线的“监控节点”。不向业务 Agent 开放观测平台密钥，也不要求 Agent 自己上报执行状态。

首版从 Python 配置执行入口到结束节点形成完整树。TS 路由和 Python 执行通过 `runId` 或请求关联 ID 查询；不把两个独立 trace 描述为一条完整跨服务 trace。

等待用户补充时结束当前 trace；续跑产生新的 trace，并关联同一 `runId` 和会话。已完成节点不重新上报成新执行，不把等待用户的时间计入节点耗时。

## 5. 数据、版本与运行记录

建议根 trace 至少包含以下元数据：

| 字段 | 用途 |
| --- | --- |
| `flowId` / `runId` | 从管理端定位一次执行 |
| `publishedVersion` / `draftRevision` | 区分发布版本与草稿修订；按执行模式记录适用字段 |
| `snapshotHash` | 唯一标识实际执行的流程配置 |
| `mode` | 区分 `test`、`production`、`evaluation` |
| `conversationId` / `attempt` | 关联会话和续跑次数；无会话的评测可省略会话字段 |
| `nodeId` / `nodeType` | 保持节点改名后的稳定关联 |
| `model` / `toolSource` | 区分模型和模拟、真实工具来源 |
| `datasetVersion` / `evaluatorVersion` | 评测时固定案例与评分规则 |

节点名称作为显示标签，不用名称代替稳定 ID。流程中的业务 traceId 与 Langfuse trace ID 分开命名，例如 `businessTraceId` 和 `observabilityTraceId`。

本地运行记录增加可选观测关联字段，续跑可保留多个 trace ID。实施时优先扩展现有 JSON 运行记录及 DTO，评估现有结构后再决定是否需要迁移，首版不为每次模型或工具调用新建业务表。

usage 不可取得时标记未知，不用 0 代替未知；成本只在有完整 usage 和相应价格配置时展示。

观测失败不改变业务执行结果；管理端保留本地记录，明确展示“未配置”“尚未上报”或“不可用”，不能把没有观测数据当作没有执行。Langfuse 查询和上报不进入聊天响应的同步依赖。

## 6. 轻量评测设计

### 6.1 数据集

首版使用仓库内版本化案例文件和一个手动评测入口，结果关联到 Langfuse。暂不开发数据集管理页面；必要时通过 SDK 同步同一份案例到 Langfuse Dataset。

先准备约 10 个案例，覆盖前端独立完成、升级后端、信息不足、工具查询未命中、节点输出不合规及工具失败。

每个案例包含：

- 稳定案例 ID、用户问题、场景标签和数据来源。
- 工具数据 fixture 或明确的只读数据来源。
- 预期分支、必经及禁止执行的节点。
- 必须出现的事实、禁止的无依据断言和必要的结果字段。
- 预期终态；故障注入案例允许以明确失败作为正确行为。

固定 fixture 适合比较编排和提示词变化，真实只读工具适合单独验证集成。两类结果分组报告，模拟案例通过不代表真实业务诊断准确。

### 6.2 执行方式

评测入口复用 Python 配置执行器，启动前冻结指定草稿或发布快照。无需启用待评测流程，不更改线上诊断绑定，不通过正式客户会话批量发消息。

评测保留独立运行标识，使用现有运行记录承载状态；是否扩展 `mode` 字段在实施阶段确认，不把评测运行伪装成正式聊天。

第一次建立已人工检查的基线，第二次比较候选配置。数据集、工具 fixture、模型参数和评分规则一致，并记录代码版本；比较时逐案例查看新失败，不能只看平均分。

先使用受限并发、总超时和调用预算。一次运行只固定执行快照，不承诺模型输出完全确定；重要案例后续可重复采样，每轮作为单独实验，避免覆盖同一案例的结果。

### 6.3 评分顺序

先做代码规则与人工检查，再考虑 LLM Judge：

| 方法 | 首版检查内容 |
| --- | --- |
| 确定性检查 | 预期终态、输出契约、分支、工具白名单、调用参数、必经节点和失败传播 |
| 人工检查 | 结论是否有依据、角色职责是否合理、信息不足是否诚实表达 |
| 可选 LLM Judge | 依据 fixture 和评分要点辅助判断事实忠实度、结论相关性及建议可执行性 |

报告至少区分执行故障、质量不达标和评分器故障。预期成功案例执行失败计入执行失败，不能仅剔除后输出更好看的通过率；评分器故障标为未评估并报告覆盖率，不伪装成答案错误。

若加入 Judge，记录模型与 rubric 版本，先与人工判定校准。流程中“综合分析 Agent”的评分属于业务输出，不能直接充当独立验收评分。

## 7. 实施阶段与验收

### 阶段 A：补齐可观测

核对现有 Provider 后，为配置执行入口建立根 trace，为节点建立正确的父子关系，复用现有模型与工具埋点；补齐失败、取消、分支和续跑记录。

验收：管理端试运行和客服正式调用各执行一次，能按 `runId` 找到正确流程版本、节点和调用；未选分支不产生执行 span；Langfuse 不可用时流程仍正常执行。

### 阶段 B：关联管理面板

在运行详情展示观测状态和受权限保护的链路链接，不复制 Langfuse 的完整查看器。不把项目密钥发送给浏览器；打开链接仍需相应 Langfuse 项目权限。

验收：管理员能从当前及历史运行定位 trace；草稿、正式运行与续跑不会串联到其他任务；未接入观测的旧记录仍能查看。

### 阶段 C：建立最小评测闭环

建立约 10 个案例、可重复执行的入口、确定性评分和人工基线。使用两份配置快照比较，产出本地报告并关联 Langfuse 实验。

验收：修改一次角色或提示词后，能看到逐案例差异、执行失败与评分覆盖率；整个评测不切换线上绑定，不污染客户聊天。

阶段 C 达标后，再评估在线抽样评分、管理端批量评测按钮和发布前检查。

## 9. 实施前需确认的信息

1. 是否已有可用 Langfuse 实例，其地址、部署版本和项目；凭据仅通过服务端环境配置。
2. 是否允许上传节点输入输出；按实际数据决定脱敏、截断和记录范围，脱敏应在发送 SDK 前执行。
3. 第一批案例及人工判定负责人；初稿可先用现有模拟数据建立编排基线。

本方案批准后再实施业务代码。第一步先验证配置流程可观测，评测建立在可核查的执行记录之上。
