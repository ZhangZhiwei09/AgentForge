# 轻量一级路由流程实施计划

日期：2026-10-10。
状态：已实施并完成本范围验收；用户于 2026-10-10 授权开始编码。服务端全量检查的既有失败见实施记录。
关联：`lightweight-agent-flow-plan.md`、`lightweight-agent-flow-implementation.md`、[本次实施记录](lightweight-entry-route-flow-implementation.md)。
可观测与评测方案暂缓，不属于本次实施范围。

## 1. 目标与验收闭环

将聊天入口部分写死的匹配条件、执行顺序、固定回复和业务路由选择提取为管理员可配置的一级流程。

一级流程只做确定性判断，返回结构化决策；后端根据决策直接回复、进入已有 Agent，或继续现有后续路由。首版不调用模型、不执行工具，不引入调度服务。

核心验收：

1. 管理员在画布配置关键词和分支，配置固定回复或目标路由。
2. 保存草稿，试运行查看逐节点匹配结果及最终决策。
3. 发布并启用，客服新请求使用发布快照。
4. 修改关键词、回复或处理去向后重新发布，无需修改后端代码或重启服务。
5. 停用一级流程后，后续新请求恢复现有入口行为。
6. 已开始的请求和等待补充的诊断任务不被配置变更截断。

“一级流程”负责请求如何分流；现有“Agent 流程”负责选定诊断场景后如何协作，两者分别配置和发布。

## 2. 已核对的现状

| 位置 | 当前行为 | 影响 |
| --- | --- | --- |
| `apps/server/src/services/agent-runtime.ts` | 问候、感谢、告别的匹配与固定回复写在 `CONVERSATIONAL_RULES`，先于 Router 执行 | 新流程启用后必须接管这个入口，否则配置可能被旧快通道提前截获 |
| `apps/server/src/services/agent-runtime/routing/l1-keyword.ts` | 固定按 SAFETY、HUMAN、DIAGNOSIS 顺序扫描正则 | 业务 L1 可配置化；安全规则保留后端保护 |

| `apps/server/src/services/agent-runtime/human-agent.ts` | 更新会话为 `escalated`，按工作时间返回固定文案与建议 | 可以接收经过校验的文案覆盖；实际转接行为继续复用 |

| `apps/server/src/routes/agent-runtime.ts` | 聊天、历史与会话接口使用既有认证、归属检查和 SSE | 保持公共请求和事件契约 |
| `apps/server/src/routes/agent-flows.ts`、Python 流程 API | 现有管理接口面向 Python 诊断流程，包含诊断专用契约 | 不直接塞入另一种 DSL |
| `apps/data-admin/src/components/agent-flows/` | 已有 React Flow 画布、配置侧栏与运行记录 | 复用依赖和交互形式，针对一级流程增加独立组件 |
| `packages/database/prisma/schema.prisma` | 已有诊断流程、通用 Workflow、意图样本和路由审计表 | 一级流程持久化要隔离，避免旧接口误读或修改 |

五层 Router 不是每次完整执行五次，而是按条件逐层尝试，得到可接受结果后停止。

## 3. 首版范围与不做事项

### 3.1 平台可配置

| 内容 | 配置形式 |
| --- | --- |
| 常见问题与业务关键词 | 任意包含、全部包含、精确匹配、排除词 |
| 判断顺序 | 条件节点的控制流顺序 |
| 命中与未命中关系 | 条件的 true / false 连线 |
| 固定回复 | 正文与建议问题 |
| 业务处理去向 | CHAT、TASK、HUMAN、DIAGNOSIS |
| 人工转接话术 | 工作时间与非工作时间两份文案、建议问题 |
| 默认处理 | 明确的 `continue` 结束节点 |
| 管理状态 | 草稿、试运行、发布、启停与最近记录 |

### 3.2 首版不做

- 修改 L2 样本管理、语义算法、L3/L4 分类提示词与阈值、L5 意图映射。
- 任意脚本、表达式、模型节点、工具节点、循环、并行、子流程。
- 自由正则输入；现有复杂正则不承诺逐条自动等价转换。
- 跨租户规则、用户自选入口、多套入口同时启用、定时调度。
- 任意指定某个诊断流程 ID，或把所有 Agent 改成配置执行器。
- 任意变量模板、HTML 回复、从用户数据构造工具参数。
- 重写安全拒绝文案、工具错误文案和各 Agent 内部 fallback。
- Langfuse 改造、评测平台建设、自动优化、发布审批。
- 新建真实人工客服队列或承诺新增客服调度；沿用当前会话升级能力。

新增业务能力仍由后端实现。平台只选择已注册的处理入口，并配置本范围内的内容。

## 4. 总体设计与执行位置

### 4.1 推荐结构

```text
管理员 -> TS /api/entry-route-flows -> 草稿 / 发布快照 / 试运行记录

客户 /api/agent/chat
  -> 原有认证、归属检查、内容安全和会话管理
  -> 后端安全优先判断
  -> 检查等待补充的诊断
     有等待任务 -> 原有续跑策略（保留安全 / HUMAN 例外）
     无等待任务 -> 选择一级流程模式
        无启用流程 -> 原问候快通道 + 原完整 L1～L5
        有启用流程 -> 固定发布快照 -> 一级流程
           reply    -> 发送配置回复，保存助手消息，结束
           route    -> 现有 Agent 分发
           continue -> 原 L2～L5 -> 现有 Agent 分发
```

一级流程在 TS 主聊天入口内执行有限条件图。它不承担多 Agent 执行，不新增第二套诊断引擎，也不要求访问 Python 后端才能进行关键词匹配或固定回复。

首版复用 React Flow 依赖、页面布局、认证客户端和发布交互形式。现有诊断编辑器含诊断输出绑定与 Agent 工具等特定语义，不为本功能整体改造成通用编辑器；确实重复的展示代码可以小范围提取，避免提前建设流程平台框架。

### 4.2 关键优先级

1. 内容安全中间件与后端 SAFETY 识别优先于平台规则，不能被配置绕过。
2. 有待续跑诊断时，沿用已有安全与人工转接例外，其余消息按旧诊断快照续跑，不执行新的一级流程。
3. 对没有待续跑任务的新消息，启用一级流程时不再经过旧问候快通道或旧业务 L1。
4. `route` 直接分发，不能再次走完整 Router。
5. `continue` 从 L2 开始；后续 L5 的旧规则兜底仍保留，不能把它误删成“重复 L1”。
6. 没有启用一级流程时，原有行为保持；不能把加载失败或配置损坏当作“没有流程”。

等待任务期间的 HUMAN 识别继续使用现有内置规则，这是首版保留的生命周期例外；普通新消息的 HUMAN 业务分流由一级流程配置。

## 5. 节点、条件与返回契约

### 5.1 五类节点

| 类型 | 行为 | 连线约束 |
| --- | --- | --- |
| `start` | 接收原始消息和后端提供的可信工作时间状态 | 唯一开始，无入边，一个后继 |
| `condition` | 对当前消息执行声明的条件 | true / false 各一个出口 |
| `reply` | 返回配置正文和建议问题 | 终态，无出边 |
| `route` | 返回目标路由；HUMAN 可附转接文案 | 终态，无出边 |
| `continue` | 交给后续智能路由 | 终态，无出边 |

回复与分流动作在返回决策前不会对外执行；图内不支持“先回复，再继续路由”。一次一级执行恰好得到一个终态结果。

执行顺序来自连线，节点坐标只影响画布。改变位置不能改变路由结果，也不另设一个与连线冲突的优先级数字。

### 5.2 条件语义

- `contains_any`：包含任意一个配置词。
- `contains_all`：同时包含所有配置词。
- `equals_any`：整个消息与任意一个配置词相等。
- `exclude_any`：命中任意排除词时，该条件整体为 false。
- 默认去除两端空白；是否忽略大小写通过明确选项配置。
- 精确匹配可选择去除末尾常见问候标点的规范化选项；限定字符集合并同步处理消息与配置词。
- 不隐式删除全部标点、不进行分词、模糊纠错或任意 Unicode 变换。
- 空字符串、空关键词集合及互相矛盾的字段在试运行与发布时拒绝。

首版只匹配当前用户消息，不扫描整个历史会话。原始消息保持不变，仅派生匹配文本；后续 Agent 仍接收原消息。

建议边界：最多 30 个节点、60 条边，每个条件最多 50 个关键词，单词最多 128 字符；回复最多 8,000 字符，建议问题最多 5 条。实际实现统一后端校验，输入消息沿用现有 16,000 字符保护，不另外放宽。

### 5.3 结构化结果

采用可辨别联合类型，禁止根据回复文案猜动作。

```typescript
type EntryRouteResult =
  | { action: "reply"; answer: string; suggestions: string[] }
  | {
      action: "route";
      target: "CHAT" | "TASK" | "HUMAN" | "DIAGNOSIS";
      handoff?: {
        withinHours: string;
        outsideHours: string;
        suggestions: string[];
      };
    }
  | { action: "continue" };
```

`handoff` 仅允许 HUMAN 使用；缺省时沿用现有人工话术。它由已发布配置产生，不能由客户端聊天请求伪造。工作时间取后端已有判断，首版不改变工作时间算法或时区。

`reply` 返回固定正文，不调用模型、知识库或记忆注入。`route` 后的模型生成内容继续由对应 Agent 和现有诊断配置决定，一级流程不覆盖其最终回答。非 HUMAN 的 route 节点首版不配置前置回复，避免重复消息及流式内容清除冲突。

结果外部包络保存 flowId、版本、运行 ID、命中的终态 nodeId、执行路径与耗时，不把完整调试信息发送给客服浏览器。

### 5.4 发布与图校验

- 唯一开始、节点和边 ID 唯一、合法类型、引用真实存在。
- 无环、无悬空节点、无不可达节点、无多路并发或隐式等待。
- 每条路径都能到达一个终态；至少存在一个可达 `continue` 兜底节点。
- 条件的两个出口完整；终态无出边。
- 回复正文非空；目标路由在白名单内；HUMAN 文案字段合法。
- 配置、节点、边、词条与记录大小有上限；执行有最大步数保护。
- 运行取消、异常或无终态明确报错，不自动当作 `continue`。

草稿可以暂时不完整；试运行与发布必须通过全部校验。

## 6. 旧行为迁移与消息兼容

### 6.1 内置初始模板

提供一个未启用的模板，例如：

```text
开始 -> 人工请求？
          是 -> HUMAN
          否 -> 问候 / 感谢 / 告别？
                  是 -> 对应固定回复
                  否 -> 故障关键词？
                          是 -> DIAGNOSIS
                          否 -> continue
```

模板固定回复采用当前有效文案与建议问题，业务词条以现有规则和回归案例为基础整理。模板始终允许在页面编辑；创建模板不自动替换当前线上入口。

现有 L1 使用正则，首版条件使用有限文本操作，不能声称所有边界完全等价。阶段 0 建立旧行为样例集，列出转换差异；默认模板的行为差异必须审查并明确记录，再决定是否启用。暂不支持的复杂匹配不能偷偷退回旧 L1。

停用后仍可以完整使用原有规则，首版不删除 `CONVERSATIONAL_RULES` 和旧业务关键词数组。

### 6.2 SSE、消息保存与人工动作

- 固定回复复用 `meta -> token -> done -> [DONE]`，保持消息 ID、会话 ID与历史契约。
- 复用普通文本 / CHAT 展示方式，不新增 `REPLY` 路由枚举或诊断卡片类型。
- 配置建议问题通过已有 `done.suggestions` 返回。
- 每条用户消息与助手消息只保存一次；固定回复必须能刷新后从历史读取。
- 固定回复也检查取消信号，不继续输出取消后的 token，不释放或重复使用其他请求的会话锁。
- 直接分流继续使用原有 RouteContext、记忆、引用、诊断进度与助手消息保存逻辑。
- HUMAN 文案覆盖进入现有 HumanAgent；不能只显示“转人工”而漏掉会话升级。
- 人工状态更新失败按既有行为记录并回归，不在本次顺带重写人工队列与事务策略。

RouteContext 仅按需新增可选的可信人工话术字段，缺省不影响其他调用方。聊天请求 DTO 不增加由普通用户选择规则、目标路由或传入话术的入口。

## 7. 持久化、授权与管理 API

### 7.1 数据存储

推荐新增两个小表，沿用现有数据库和 Prisma 迁移体系：

| 表 / 建议模型 | 保存内容 |
| --- | --- |
| `entry_route_flows` / `EntryRouteFlow` | 草稿、修订号、发布快照、发布版本、启用、归档、操作者与审计时间 |
| `entry_route_flow_runs` / `EntryRouteFlowRun` | 实际配置快照、试运行或正式模式、会话与助手消息关联、节点记录、最终决策、状态、错误与耗时 |

选独立表的原因：当前 Python AgentFlow API 的保存、校验、发布与执行均采用诊断 DSL；通用 Workflow 的用户所属、表达式和执行语义也不同。强行共表会扩大兼容修改范围。两个 JSONB 表不引入新的数据库服务，也不为节点、角色或每个版本单独建表。

流程软归档，历史运行保持可查。新表使用专属索引保证全平台至多一个入口流程启用，并约束启用流程必须已发布且未归档；启用切换在事务中串行执行。

发布前锁定目标记录并检查修订号，校验后原子更新快照与版本。一次聊天请求只选一次启用流程和发布快照，后续不读取最新草稿；发布或启停只影响后续请求。

首版直接读取数据库中的当前发布快照，避免无效的进程缓存导致多实例发布不生效。若后续实测需要缓存，再设计版本失效机制，不先增加 Redis 依赖。

一级运行记录只描述“决策是否完成”，不把后续 Agent 的成功或失败冒充为一级结果。关联现有会话和助手消息即可追踪后续响应，暂不重写诊断运行 ID 链路。

执行前创建运行记录，纯判断完成后一次保存有上限的节点记录及决策；不逐节点写库。异常和取消更新终态；保存正式决策失败时，在对外发送回复或执行分流动作前明确失败。进程崩溃留下的 running 记录不宣称支持自动恢复。

### 7.2 管理 API

建议新增 TS 原生 `/api/entry-route-flows`，不经过 Python 代理：

| API | 用途 |
| --- | --- |
| `GET /api/entry-route-flows` | 流程列表 |
| `POST /api/entry-route-flows` | 从模板或最小空图创建 |
| `GET /api/entry-route-flows/{id}` | 详情 |
| `PUT /api/entry-route-flows/{id}/draft` | 带修订号保存 |
| `POST /api/entry-route-flows/{id}/validate` | 校验已保存草稿 |
| `POST /api/entry-route-flows/{id}/test-run` | 校验并执行草稿快照，返回 JSON 决策与节点记录 |
| `POST /api/entry-route-flows/{id}/publish` | 发布指定草稿修订 |
| `PUT /api/entry-route-flows/{id}/activation` | 启用或停用 |
| `DELETE /api/entry-route-flows/{id}` | 软归档并停用 |
| `GET /api/entry-route-flows/{id}/runs` | 分页读取记录，区分试运行与正式 |
| `GET /api/entry-route-flows/{id}/runs/{runId}` | 运行详情 |

确定性试运行无需模型等待，首版返回 JSON，不增加运行队列、单独 SSE 或暂停续跑接口。试运行只产生决策，不能真正发送客户回复、转人工、调用下游 Router 或切换线上绑定。

所有管理接口和调试记录要求管理员权限；页面隐藏入口不是授权措施。过期登录返回 401，普通用户返回 403，修订冲突返回 409，字段与图错误返回明确的校验路径。

记录在写库和响应管理员之前脱敏、截断；不得保存密钥、认证头或完整未受限历史。复用现有脱敏方式前核对适用范围，不因复制诊断记录逻辑而引入 Python 网络依赖。

## 8. 修改位置清单

路径名称为建议；实施时保持现有目录风格，不进行无关重构。

### 8.1 必须修改或新增

| 文件 / 模块 | 改动 | 验证重点 |
| --- | --- | --- |
| 新增 `apps/server/src/services/entry-route-flows/{schema,runtime,service,templates}.ts` | 有限 DSL、校验、确定性执行、模板和持久化 | 终态、分支、快照、无模型与工具 |
| 新增 `apps/server/src/routes/entry-route-flows.ts` | 管理员 API、冲突与错误响应 | 普通用户不能读写或试运行 |
| `apps/server/src/app.ts` | 注册新管理路由 | 认证、内容安全和既有路由不受影响 |

## 10. 回归范围与用例矩阵

### 10.1 一级执行与契约

| 场景 | 必须验证 |
| --- | --- |
| 条件命中 / 未命中 | any、all、equals、exclude，大小写、空白、中文与标点规范化 |
| 多个条件都可匹配 | 只走实际控制流选中的路径，不按坐标或节点名称决策 |
| 固定回复 | 内容与建议准确，无模型、工具、L2～L5 或记忆注入 |
| route | 目标 Agent 只执行一次，不重新分类；DIAGNOSIS 沿用启用流程 |
| continue | 跳过旧快通道与业务 L1，L2～L5 顺序、阈值和降级保持 |
| 无效配置 | 循环、悬空引用、不可达、缺出口、非法字段及过大配置均拒绝 |
| 无终态 / 执行异常 | 明确错误，不伪装完成或继续后续路由 |
| 配置注入 | 文案按普通内容输出，目标与参数按枚举和 schema 校验 |

### 10.2 主聊天入口与旧路径

| 场景 | 必须验证 |
| --- | --- |
| 一级流程未启用 | 旧问候、感谢、告别、转人工、诊断及 L2～L5 与基线一致 |
| 新流程覆盖问候 | 旧固定回复不会先返回，平台配置实际生效 |
| 安全消息同时命中业务词 | 拒绝或进入 SAFETY，不能得到业务固定回复 |
| 已等待补充 | 普通补充继续旧诊断；保留明确转人工与安全例外 |
| 等待期间发布或停用 | 不改变待续跑诊断快照，不重新执行已完成专家 |
| HUMAN | 配置文案、生效时段、状态升级、旧默认文案及数据库失败行为 |
| 会话与历史 | 登录身份、会话归属、历史正确、助手消息只保存一次 |
| 客户断开 / 取消 / 并发 | 不输出取消后内容，锁正常释放，不串会话记录 |
| 启用配置加载失败 | 返回明确错误，不进入旧流程隐藏故障 |
| DIAGNOSIS 后端失败 | 保留现有明确失败，不自动重跑旧团队 |
| 其他处理入口 | 普通问答、工具结果、记忆注入、引用与过程记录不回归 |

### 10.3 发布、权限与数据

- 普通用户对列表、详情、保存、发布、启停、试运行和运行记录均得到 403。
- 无效登录返回 401；配置失败不清除有效管理员会话。
- 两个标签页保存、保存后旧修订试运行或发布得到 409。
- 未发布不能启用；发布草稿不会误启用另一流程。
- 并发启用两个流程，最终只有一个启用；发布与启用切换没有混合快照。
- 请求使用 v1 时发布 v2，请求继续按 v1，后续请求使用 v2。
- 试运行使用草稿修订，不调用正式 Agent，不更新真实客户会话或线上绑定。
- 归档、停用和数据库迁移不删除历史记录；运行详情归属正确。
- 脱敏、截断、分页和旧记录缺少可选字段均可处理。

### 10.4 浏览器与既有 Agent 流程

- 管理员完成新建、加节点、连线、编辑、保存、试运行、发布、启用和停用。
- 草稿错误定位到具体节点，未保存与未发布状态准确。
- 连续拖拽不闪屏或白屏；编辑不重置视口；删除节点同步删除引用边。
- 桌面与窄屏检查文本、工具栏、侧栏和运行面板，不产生遮挡。
- 管理员切换、退出、普通用户直接打开页面按原规则工作。
- 现有核身画布、草稿试运行、发布启停与正式聊天不回归。
- 客服端固定回复、建议问题、人工响应及动态诊断卡片正常；刷新历史仍正确。

## 13. 发布与回滚

1. 先部署新表与兼容代码，新一级流程默认停用。
2. 创建模板、核对转换差异、试运行并保存验收样例。
3. 在隔离环境验证客服三种动作、旧路径和等待任务。
4. 发布后明确启用，观察运行记录和错误，不按模板创建自动启用。
5. 需要回滚时停用一级流程，新请求恢复旧问候和完整 L1～L5；原诊断流程绑定不变。

回滚不删除新表与历史记录，不撤回当前请求已经固定的快照。恢复历史配置可从已保存快照重新建草稿并发布新版本，不减少版本号；首版不建设完整历史版本管理。

入口故障不可访问管理页面时，保留有文档说明的服务端停用操作，操作目标应明确限定一级启用绑定；不新增普通用户可访问的紧急停用端点。

最终交付以“平台修改关键词、文案、分支和目标，发布后生效，停用可恢复”为标准，不以画布能够保存 JSON 为完成标准。
