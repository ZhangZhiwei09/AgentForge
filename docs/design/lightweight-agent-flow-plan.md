# 轻量多 Agent 流程配置实施计划

> 日期：2026-10-07
> 状态：已批准实施，首版执行与管理端已落地；验证与启动说明见 `lightweight-agent-flow-implementation.md`。
> 定位：现有 Agent 执行能力的轻量编排配置，不建设完整的 Dify。
> 首个接入场景：现有 TS 客服 DIAGNOSIS 入口，通过签名桥接调用 Python 配置执行器。

## 1. 目标

让管理员通过平台配置部分多 Agent 协作，不再为修改角色、节点任务或合法执行关系直接修改业务编排代码。

第一版必须形成真实闭环：

1. 在管理端配置 Agent 身份、任务、工具、输入输出及简单分支。
2. 保存草稿，试运行并查看各节点的输入、输出和状态。
3. 发布并启用，现有客服诊断入口使用已发布配置。
4. 修改草稿或发布新版本，不影响正在执行或等待用户补充的旧任务。
5. 没有启用配置时，原有诊断路径保持原样，其他 Agent 场景不受影响。

第一版的关键验收案例：在诊断流程中新增一个“数据库排查专家”节点，选择已有工具、配置任务和输入，并接入合法位置；无需修改编排代码，即可在试运行和真实诊断中执行、展示结果。

这里验证的是新增角色与任务编排，不承诺仅通过提示词获得新能力。新增数据库访问等工具实现仍需开发。

## 2. 范围与非目标

| 平台负责配置 | 后端继续负责实现与约束 |
| --- | --- |
| Agent 名称、身份、职责和系统提示词 | 模型调用、ReAct 执行、消息封装 |
| 节点任务、合法顺序和简单条件分支 | 工具实现、授权、安全策略 |
| 显式输入映射、结构化输出声明 | 超时、取消、运行预算、错误处理 |
| 草稿、试运行、发布和启用 | 诊断强制升级规则、评分决议、结果适配 |

第一版包含：

- 轻量画布：添加、移动、删除节点，连线，点击编辑。
- 四种节点：开始、Agent、条件、结束。
- 串行执行与二选一条件分支，不允许循环、并行及隐式汇合等待。
- Agent 身份直接定义在节点中，不建设独立角色库。
- 模型继承平台现有配置，不新增节点级模型供应商管理。
- 仅选择已注册且当前管理员可配置的工具。
- 节点级超时和迭代上限，但不得超过后端全局预算。
- 草稿保存、试运行、节点记录查看、发布与启停。
- 单一平台诊断绑定；第一版只允许一个已发布流程被启用。

明确不做：

- 全平台路由配置化、普通问答和其他任务迁移。
- Agent 自主委派、主管动态调度、并行协作。
- 子流程、循环、代码节点、任意表达式或动态脚本。
- 独立工具市场、插件机制、模型管理和新知识库管理。
- 独立角色库、跨流程角色引用及其版本联动。
- 多人实时编辑、复杂审批、流程定时调度。
- 单节点断点调试、任意节点恢复、自动重跑有副作用的工具。
- 完整复制或移植 Dify 的前后端、执行引擎。

“轻量”通过限制功能边界实现，不省略授权、配置校验和运行版本隔离。

## 3. 已确认的项目基础

| 位置 | 当前情况 | 对本计划的影响 |
| --- | --- | --- |
| `apps/server-py/src/agent/diagnosis/route_agent.py` | 角色定义和名称到阶段的映射固定在代码中 | 需要配置加载和动态节点事件映射 |
| `apps/server-py/src/agent/diagnosis/graph.py` | 诊断父图的节点、边和分支固定 | 复用 LangGraph，增加受约束的配置图构建 |
| `apps/server-py/src/agent/diagnosis/mode.py` | 当前执行入口已委托 LangGraph 图 | 不能依据旧设计文档假定仍是手写执行主路径 |
| `apps/server-py/src/agent/executor.py` | 已有 Agent 执行器 | 复用，不重写 ReAct 引擎 |
| `apps/server-py/src/agent/tools/registry.py` | 支持注册、过滤和执行工具 | 按节点创建严格的工具白名单 |
| `apps/data-admin/src/App.tsx` | 管理端尚无流程配置页面 | 新增管理路由及导航入口 |
| 两个前端的 `vite.config.ts` | 代理默认指向 `8000`；实施时确认实际运行的是 TS 服务 | 保留 TS 公共入口，管理接口薄转发，配置诊断使用签名桥接 |
| TS `teams/`、`workflows/` 与 Prisma 模型 | 已有团队及工作流基础，但不是当前 Python 诊断的配置入口 | 借鉴定义，不直接假定现有引擎可接管 |
| `packages/cui/src/cards/DiagnosisCard.tsx` | 部分显示行为依赖固定诊断阶段 | 新节点的展示和跳过状态需要回归验证 |

现有运行时需要特别验证：

- `graph.py` 中空工具列表当前会选择完整注册中心；新配置路径必须明确 `tools: []` 表示禁用全部工具。
- `AgentRole.max_iterations` 已存在，但当前 `AgentExecutor` 构图使用全局常量；表单字段不能只保存而不生效。
- 现有诊断 prompt builder 会拼接 Blackboard，不能直接沿用这一行为并声称后端仅看到显式映射的事实数据。
- 自定义节点失败不能被收集 token 的逻辑误判为正常完成，需识别执行器的错误事件。
- 当前 HITL 关联主要保存在内存中；配置路径需要持久化运行关联与版本，避免续跑误用新配置。

## 4. 总体接入

```text
管理端 → TS 管理 API 薄转发 → Python 流程 API → 草稿 / 发布快照
                                     ↓
                               配置校验与试运行

现有客服入口 → 现有意图路由
                 ├─ 普通问答 / 其他任务 → 原有执行逻辑
                 └─ DIAGNOSIS
                      ├─ 无启用配置 → 原有 TS 诊断团队
                      └─ 有启用配置 / 等待续跑 → 签名桥接 → Python 固定运行快照 → 配置诊断图
```

实现原则：

1. 新增独立、范围小的流程配置模块，复用现有执行器、工具注册中心、模型解析、日志和父图 checkpoint 能力。
2. 首版只为 DIAGNOSIS 接入，不同时维护 TS 和 Python 两套配置执行器。
3. 开始执行前固定完整配置快照；节点执行和续跑都不读取最新草稿。
4. 不向模型注入整个流程图、完整共享上下文或其他节点的全部结果。
5. 配置执行失败明确返回错误，禁止自动切回旧诊断图重新执行，避免重复工具调用和隐藏失败。
6. 无启用流程时才走旧路径；已启用但加载失败时明确报错，不静默替换执行版本。

实施校正：TS 与 Python 必须共享业务数据库及 JWT 密钥。Python 独立聊天入口本次不接管配置流程；Python 只维护一套配置执行器，TS 不新增第二套引擎。原有 Python 固定诊断图保持不动。

## 5. 配置结构与执行语义

### 5.1 流程定义

建议用一份带 `schemaVersion` 的 JSON 保存：

- `nodes`：节点 ID、类型、名称、配置。
- `edges`：来源、目标及条件节点的 `true` / `false` 出口。
- `diagnosisBindings`：指定前端排查、后端排查、汇总节点的 ID。
- `outputAdapter`：首版固定为后端内置的 `diagnosis_v1`。
- `limits`：流程总超时和总迭代预算。
- `nodes[].position`：节点画布位置，仅影响展示，不参与执行；首版不持久化视口。

身份和任务在数据结构中分开，在第一版界面中共同编辑：

| 节点区域 | 主要字段 |
| --- | --- |
| 身份 `role` | 名称、职责、系统提示词 |
| 任务 `task` | 本节点任务说明 |
| 输入 `inputs` | 命名输入到用户问题或上游结果字段的映射 |
| 输出 `outputs` | 字段名、类型、必填标记 |
| 执行 `execution` | 工具白名单、超时、最大迭代次数 |

`nodeId` 是执行标识，名称只是显示文案。改名不能破坏引用，同一身份也不意味着共享执行状态。

首版限制建议：最多 10 个 Agent 节点；不开放任意规模图。数值边界在实施前核对当前全局限制。

### 5.2 四类节点

| 类型 | 行为 |
| --- | --- |
| 开始 | 接收原始用户问题和后端提供的可信运行元数据 |
| Agent | 用配置身份及显式输入执行任务，校验结构化输出 |
| 条件 | 对一个已声明的输出字段进行类型匹配的比较 |
| 结束 | 调用内置结果适配器，形成现有诊断输出 |

首版条件只支持 `eq` / `ne`；不提供 JavaScript、Python、`eval` 或自由表达式。

Agent 输出类型首版支持 string、number、boolean、object、array；object、array 可作为整体映射，暂不建设复杂嵌套 schema 编辑器。已有诊断输出使用内置契约做进一步校验。

必须将控制字段解析为真实类型；字符串 `"false"` 不能当成布尔值。输出缺失或类型错误则节点失败，不自动猜测分支、不偷偷补成成功结果。

### 5.3 控制流与数据流分离

- 连线只定义控制流，不自动传递所有上游结果。
- 输入引用采用结构化字段路径，如 `{ source: "node", nodeId: "...", path: ["context_for_backend"] }`。
- 节点只得到映射后的输入和指定任务；系统身份与用户数据分别封装。
- 条件节点只执行一个出口，未选分支中的节点记为跳过。
- 汇合是互斥分支的控制流汇合，不是多个分支并行后等待。
- 发布校验保证必填引用在每条可达路径上都存在；不能引用未来节点或只在另一分支产出的值。
- 工具调用通过过滤后的注册中心执行，不仅过滤提供给模型的工具描述。

## 6. 首个诊断模板与业务保护

```text
开始 → 前端排查 → 是否需要升级
                   ├─ 否 → 前端结束
                   └─ 是 → 后端排查 → 综合分析 → 诊断结束
```

平台允许在合法位置插入其他专家节点，例如后端排查与综合分析之间。新增专家的结果通过显式映射进入综合分析任务；保留原有前后端评分及最终诊断契约。

第一版不是任意业务流程引擎，诊断模板有以下约束：

1. 前端、后端、汇总是内置任务契约，通过节点 ID 绑定，不再依赖固定显示名称。
2. 前端输出由后端内置策略执行强制升级检查，条件节点读取检查后的结果。
3. 后端默认只读取原始问题与前端事实字段，不注入前端结论或全量 Blackboard。
4. 升级路径必须经过后端及汇总，不能靠修改连线绕开强制诊断规则。
5. 综合评分、分歧处理和信息不足判定继续复用代码中的确定性规则。
6. 模板生成时完整迁移当前有效职责和输出要求；平台编辑不能删除内置输出契约及安全约束。
7. 现有信息预检和 HITL 保留。HITL 作为内置诊断行为处理，不新增一个通用人工审批节点。
8. 用户补充后按旧运行快照及旧 checkpoint 续跑，不重新执行已完成的专家节点。

这意味着“自由增删专家节点”与“核心诊断步骤任意删除”不同。首版只承诺前者及合法顺序调整。

## 7. 持久化、发布和授权

### 7.1 最小持久化

建议新增两张职责明确的表，不为节点、边、角色和每个版本分别建表：

| 表 | 内容 |
| --- | --- |
| `AgentFlow` | 名称、场景、草稿 JSON、草稿修订号、已发布 JSON、发布版本、启用状态、审计时间及操作者 |
| `AgentFlowRun` | 流程 ID、发布版本或草稿修订号、完整配置快照、操作者、会话关联、运行状态、节点记录 JSON、结果、checkpoint 关联、耗时 |

已有 `Workflow` / `AgentTeam` 的 DSL、所属用户语义及 TS 接口与新功能不同。首版不强行把新配置写入这些表，避免旧接口误读和修改配置；新增模型前检查实际数据库状态和迁移历史。

数据库结构以现有 Prisma migration 链为唯一变更入口，Python SQLAlchemy 映射对齐，不另建第二套迁移体系。

两张表即可保存运行所需的版本快照；暂不提供完整历史版本浏览。软归档流程，不能删除运行快照或破坏待续跑任务。

### 7.2 发布规则

- 保存只更新草稿；试运行保存当前草稿快照但不绑定线上入口。
- 发布先做完整校验，再原子更新已发布快照和递增版本。
- 发布与启用分别控制，避免新流程试验时意外替换线上配置。
- 同一场景只能启用一个已发布流程，切换须在事务中执行并有数据库唯一性保护。
- 草稿保存和发布携带修订号；过期修订返回冲突，防止两个浏览器标签页覆盖修改。
- 已开始的运行继续使用运行快照；取消绑定只影响新的诊断请求。

第一版采用平台级诊断配置，只允许已有管理员角色管理、发布和试运行。普通用户只能经正常客服入口使用启用流程，不能自行选择其他流程或读取其节点调试数据。

所有管理与运行详情 API 检查权限；复用现有认证，但不能只依赖前端隐藏入口。

运行日志保存前沿用或补齐敏感字段脱敏与大小上限；密钥不得写进流程 JSON、节点输出或浏览器日志。

## 8. 最小管理 API

建议使用 `/api/agent-flows`，避免与既有 `/api/workflows`、`/api/teams` 混淆：

| API | 用途 |
| --- | --- |
| `GET /api/agent-flows` | 流程列表 |
| `POST /api/agent-flows` | 创建流程，可从内置诊断模板初始化 |
| `GET /api/agent-flows/{id}` | 获取详情及草稿、发布状态 |
| `PUT /api/agent-flows/{id}/draft` | 保存草稿，检查修订号 |
| `POST /api/agent-flows/{id}/validate` | 校验指定草稿 |
| `POST /api/agent-flows/{id}/test-run` | 草稿试运行，返回运行 ID 和 SSE |
| `POST /api/agent-flows/{id}/publish` | 发布指定修订 |
| `PUT /api/agent-flows/{id}/activation` | 启用或停用诊断绑定 |
| `GET /api/agent-flows/{id}/runs/{runId}` | 获取已保存的试运行或正式运行详情 |
| `POST /api/agent-flows/{id}/runs/{runId}/cancel` | 取消运行 |
| `GET /api/agent-flows/tools` | 当前允许选择的工具 |

取消复用现有运行控制机制，不单独引入队列或调度服务；日志持久化不等于首版提供任意崩溃重放。

## 9. 前端与事件兼容

管理端增加“Agent 流程”入口和列表，编辑页面采用：

- 中间：轻量节点画布。
- 右侧：当前节点配置。
- 试运行区域：用户问题输入、节点状态、输入输出、错误和耗时。
- 顶部：保存、试运行、发布及启用状态。

使用成熟的 React Flow 类画布库；实施时核对当前依赖、API 和兼容版本。参考 Dify 交互组织，不直接复制其组件、设计系统和后端绑定体系。

界面必须标记未保存、未发布、运行中、失败及字段错误。发布和试运行前反馈具体节点及字段的校验失败，不只显示“流程无效”。

客服端事件兼容：

1. 保留现有诊断启动、阶段进度、完成和等待输入语义。
2. 阶段以稳定 `nodeId` 标识，标签来自节点名称；阶段序号按配置确定，不能依赖三个固定角色名。
3. 契约扩展保持旧诊断消费者可用，更新 shared-types、SDK、两个聊天事件消费者及诊断卡片。
4. 旧快路径行为保留；自定义分支的未执行节点正确显示为跳过，不能简单按 `phase > 1` 推断。
5. 客服端只展示适合用户查看的摘要，完整节点输入、工具细节和调试记录只在授权管理端显示。

## 10. 校验与运行保护

草稿允许暂时不完整；发布和试运行要求完整合法：

- 唯一节点 ID、合法节点类型、恰好一个开始、至少一个结束。
- 节点、边、输入引用真实存在，无环、无悬空节点、无不可达节点。
- 开始无入边；结束无出边；普通节点只有一个后继；条件必须有 true、false 出口。
- 任一路径均可结束；禁止并行分叉及不确定调度。
- 必填输入在所有可达路径可用，比较值与输出声明类型一致。
- 工具已注册且授权；显式空列表保持零工具。
- 内置诊断绑定完整，输出契约和业务强制规则不能被绕过。
- 超时、迭代数、节点数量、输入输出大小受后端上限限制。
- 运行错误、取消和总超时均产生明确终态，不继续伪装成功。

第一版默认节点失败即终止流程，不提供用户可配置重试。内置诊断已有的重试行为须审查副作用，不能把原有超时重试未经评估推广到所有新节点。

## 13. 预期修改范围

预计新增 Python 流程模块、API、ORM 模型和相关测试；模块命名以实施时的实际组织为准，不提前引入大型服务层框架。

主要对接位置：

- `apps/server-py/src/agent/diagnosis/`：配置接入、内置业务策略、事件与续跑适配。
- `apps/server-py/src/agent/executor.py`：有限的执行参数接入，避免改变其他路由默认行为。
- `apps/server-py/src/agent/tools/registry.py`：按需完善配置路径的严格过滤和授权。
- `apps/server-py/src/api/`、`src/models/`、`src/main.py`：新模块注册及认证接入。
- `packages/database/prisma/`：schema 与迁移。
- `packages/shared-types/`、`packages/sdk/`：最小接口及兼容事件契约。
- `apps/data-admin/src/`：流程管理页面和导航。
- `apps/customer-service/src/`、`packages/cui/src/`：动态阶段与跳过状态。

不重构无关模块，不修改 Dify 源码，不覆盖已有工作区变更，不同时改造 TS 团队和工作流引擎。

## 14. 后续扩展原则

第一版达标后，根据真实需要再决定独立角色库、更多接入场景、并行节点或主管调度；这些不计入本次交付。

每增加一种能力，必须同时回答：配置如何定义、执行如何限制、结果如何追踪、版本如何固定。不能仅增加一个画布节点而没有完整执行语义。

参考：本地 Dify 的 Agent V2 身份绑定与节点任务分离、显式输出引用、草稿发布隔离；AgentForge 的 `multi-agent-langgraph-plan.md` 提供复用背景，实际实现以当前代码为准。
